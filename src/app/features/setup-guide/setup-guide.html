Setup Guide

Device setup, service configuration, and troubleshooting reference

Overview

This service receives attendance and device traffic from ZKTeco-family biometric machines and pushes processed attendance rows into the ERP attendance tables.

Attendance flows in four steps: the device pushes a raw log → the service queues it for processing → it's parsed into a normalized attendance row → an ERP sync worker periodically (or on demand) pushes pending rows into the ERP database.

Device setup

On the physical device, under Comm. → Ethernet / Cloud Server Setting (ADMS):

  1. Enable Cloud Server Mode / ADMS.
  2. Set Server Address to this service's host (domain or IP).
  3. Set Server Port to the port this service listens on.
  4. Leave Enable Domain Name off unless the server address is a hostname, not an IP.
  5. Set the device's own Date/Time correctly and to the correct time zone before connecting it — see Timezone & time sync. This service deliberately never sets or corrects a device's clock.
  6. Save and let the device reconnect. It should appear on the Devices screen within about 30–60 seconds (see Verify communication).
New device default A newly-seen device starts with ERP syncing off by default. Attendance still gets recorded locally, but nothing is pushed to ERP until someone explicitly turns on "Start syncing" for that device on the Devices screen.

Supported machine information

This service supports current ZKTeco ADMS push devices — the SpeedFace series, uFace 800, and most current ZKTeco push-SDK machines — as well as older Nedo/FK-protocol machines.

A device's protocol is recorded automatically the first time it connects and shown on the Devices screen.

Connecting a Nedo/FK machine? Use its Cloud ID, not its printed serial number. These older devices identify themselves with an auto-generated Cloud ID — a hex-style string the device itself sends on every request — which is not the same as the serial number printed on the device's label. If you register the printed serial number instead, the device will keep connecting successfully but will never be recognized as the same machine, and its attendance won't be linked up. Always use the Cloud ID when registering this type of device.

Timezone / time synchronization requirements

This service never sets a device's clock After repeated confirmed cases of devices' clocks being corrupted by server-driven time updates, this service was changed to never send or correct a device's time in any way. Each device must have its own correct local date, time, and time zone configured directly on its own menu before (and independently of) connecting to this service.

The service assumes every connected device's own clock is correctly set to the configured default time zone (currently Pakistan Standard Time, UTC+5, no DST) — that assumption is only used to convert a device's reported local timestamp for storage and ERP sync. If a device's own clock is wrong, its attendance timestamps will be wrong even though nothing was sent to the device.

Checklist before connecting a device

  • Set the device's date, time, and time zone manually and correctly.
  • If the device has its own NTP / "auto sync time" option, review it — a device that keeps its own time server in sync shouldn't conflict with this service (which never touches device time), but a misconfigured one is a common source of drift independent of this server.
  • After connecting, periodically spot-check the device's own screen time against real time — see 3-hour / 5-hour time issue for what to do if it drifts.

Troubleshooting steps

  1. Check the service's health check responds OK — confirms the service itself is up.
  2. Check the Devices screen — is the device listed, and was it seen recently? If not, it's a network/connectivity problem, not application logic (see Verify communication).
  3. Check that device's machinelog folder (below) for the exact raw request/response traffic.
  4. Check the Raw Logs screen for parsing errors on that device's pushes.
  5. Check the Attendance screen, filtered to that device, for the sync status and reason columns — Synced / Pending / Skipped (with reason) / Failed.
  6. If rows are stuck Skipped because syncing was off for that device, toggle "Start syncing" on the Devices screen — this also re-queues its previously-skipped backlog automatically. If they're stuck for any other reason (e.g. not registered in ERP), use the Re-sync screen once the underlying cause is fixed.

Logging / debugging instructions

Every device-facing request and response is written to a plain text file under the service's machinelog/ folder, split per device so one machine's traffic never mixes with another's: 

machinelog/
  {SerialNumber or Cloud ID}/
    2026-08-17.log
    2026-08-18.log
  _unknown/
    2026-08-17.log   ← requests where the device's identifier couldn't be resolved

Each line is one of three kinds:

  • REQ — what the device sent.
  • RES — what the service sent back, including status.
  • ERR — an error the service hit while handling that request. The device usually still gets a normal-looking reply (so it stays connected), so this is the only place that failure is visible.

To investigate one machine end-to-end: open its folder, read chronologically — every REQ is immediately followed by its RES (and an ERR line if something broke while producing that response).

This is separate from the database machinelog is a plain-file debugging aid independent of the Raw Logs screen and the database — useful for handing raw evidence to a device vendor, or reading directly on the server when the API/DB aren't trusted to be behaving correctly.

Steps to verify device-to-service communication

  1. From a machine on the same network path as the device, confirm the configured port is reachable.
  2. On the device menu, confirm the configured Server Address and Port match this service exactly.
  3. Watch that device's machinelog file — you should see recurring check-in and data-push requests roughly every 30 seconds once connected.
  4. Confirm the device appears on the Devices screen with a recent last-seen time and status "Online".

Steps to verify attendance synchronization

  1. Confirm syncing is turned on for the device (Devices screen → "Start syncing").
  2. Take an attendance punch on the device.
  3. Confirm it shows up on the Attendance screen for that serial/PIN with status "Pending".
  4. Click Sync attendance now (top of the Attendance screen), or wait for the background sync interval.
  5. Confirm the row's status changes to a timestamp (Synced). If it instead shows "Skipped" or "Failed", check the reason column next to it.
  6. The notification bell (top bar) shows live progress of any in-progress sync run.

Known issue: 3-hour / 5-hour time drift

Status: open / under investigation Some devices have been observed jumping several hours after connecting to this service. This has been investigated repeatedly; several server-side causes have been found and removed, but the symptom has been reported again since, so it is not considered fully resolved.

What has already been ruled out on the server side

  • The service used to answer the device's time-check request with its own clock — removed. It no longer answers this request at all.
  • The service used to send timezone/sync-time fields in its normal options reply to devices — removed. Confirmed via a direct device test (removing/re-adding the server URL) that these fields were misapplied by at least one device model.
  • The service does not issue any time-set command to devices — every response observed in production logs for the device's periodic check-in has been a plain acknowledgement or a queued, unrelated user-management command.

Current leading hypothesis

With the above removed, the remaining explanation is device-side: the device's own firmware NTP behaviour, tied to its Proxy Server / Web Server URL settings, appears to re-sync its clock independent of anything this service sends. This has not yet been proven conclusively for every affected device or model.

What to do if you see this

  1. Note the exact device model, firmware version, and the time before/after the drift.
  2. Check that device's machinelog folder for the time window the drift happened in — capture it before it rotates out.
  3. On the device itself, check whether it has its own NTP / "auto sync" setting under Date/Time or Proxy Server / Comm settings, and note whether it's enabled.
  4. Report the above details so the machinelog evidence can be reviewed — do not assume this is fixed by anything already deployed.
